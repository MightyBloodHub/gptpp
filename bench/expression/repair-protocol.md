# Choosing among edits that satisfy the examples

This development comparison uses the Redis, FastLED and Go scalar extracts from the expression study. The tasks, two local model digests and archived GPT++ catalog outcomes are fixed before collecting new model replies. Both workflows receive the target function, change request and the same three public examples for each task. The new workflow can run those examples during search. Each model sees each task once. No trial receives the reference location, reference expression, withheld inputs or withheld outputs.

Run the ordinary repair CLI on the original module with its default search budget. For every nonempty menu, use one structured model call to choose a numbered edit or abstain, including when only one edit is available. Keep empty searches, abstentions, rejected edits and wrong answers in the denominator. Stop after the first choice. Apply the published expression using its checked source revision and byte span. Score its public and withheld behavior through the original benchmark evaluator. After the choice is fixed, score the first candidate under the same checks as a deterministic control. The control never changes which edit the model publishes.

Use both Ollama models and seed 42 as in the catalog study. Use the original catalog's GPT++ row order. Record the exact inference request and reply, reported input and output tokens, search counts, observed CLI wall time and inference round-trip time. The CLI clock includes model metadata, candidate search and validation. The independent scorer runs outside that clock. Empty searches use zero model tokens. Keep model costs separate from machine search time. Report tokens per accepted edit only when at least one edit passes. The prior catalog was run at its archived compiler revision and any comparison is descriptive.

A corrected change must pass every public and withheld case. Evaluate separately by task and model. Two model choices on the same three starter programs do not make six independent tasks. The corpus and previous failures were visible during development. These results describe GPT++ maintenance on these fixtures and do not qualify a general efficiency claim or compare this search against matched Python or Rust implementations.
