# Model-generated edits checked against finite contracts

Use the same three frozen modules and independent oracles as the finite-contract study. After that study, the product gained an optional contract-guided generation mode. These development fixtures and earlier results were visible to the project team. This follow-up tests the finished CLI from its normal entry point. It is a separate observational study of two local models generating GPT++ expressions.

Run Qwen2.5-Coder 7B, then StarCoder2 3B, with their exact archived local Ollama digests. Each model receives the carry, capacity and block fixtures in that order. Supply the original module, target function and the identical request template: “Repair FUNCTION to satisfy the declared contracts.” Replace FUNCTION with the target name. Use contract mode with the product's default verification and generation budgets. Do not supply sparse examples, a candidate menu, a reference edit, oracle output, extra probes or any additional hints. Permit at most the CLI's one diagnostic retry on the unchanged source. A successful proposal ends generation immediately. Failures stay in the denominator and contribute all their tokens.

Record each request, raw model response, local token counts, validation outcome and source revision. Use the published fragment and guarded apply command to materialize the exact selected edit. Afterwards, run direct calls on every declared tuple and the five fixed extra inputs with the independent oracle. Only full-domain correctness counts as acceptance. Report extra behavior separately. Record first-attempt and final acceptance, retries, total tokens, tokens per accepted edit when defined and observed wall time. Replay archived completions through the normal CLI on loopback and compare the generated requests, selected edits and results. This study collects no Python or Rust model responses. It has no matched free-generation baseline on these fixtures.
