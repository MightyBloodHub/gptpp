# Expression-level maintenance study

Freeze the fixtures, model digests, prompts, editing adapters and analysis rule before the scored calls. Each fixture extracts a historical change expressible at one existing scalar expression. The experiment supplies the target function. Every language has a checked starter, two existing caller paths, public examples and withheld tests. Pinned upstream sources document the scope of the extraction.

Each model tries four workflows in each of GPT++, typed Python and Rust.

| Workflow | Information and budget |
|---|---|
| Body | Fill the whole target body in one call using the established maintenance prompt. |
| Given expression | Supply the correct old expression and its position in the target. Fill only that expression in one call. This estimates the cost when an editor or user provides the site. |
| Locate and edit | Supply the task, public examples and original target function. A first call copies one existing expression. Resolve that text to a unique expression in the language's syntax tree. On success, a second call fills that expression. Charge both calls. The fixture's known location plays no part in selection. |
| Locate and edit in one call | Give the same target and examples. Prompt for a two-line change with a prefilled minus sign, the old expression, then a plus sign and its replacement. Resolve the old text to one syntax node and validate the new expression. Charge the full call, including malformed answers. |

The primary comparison uses **locate and edit on Qwen2.5-Coder 7B versus typed Python locate and edit**, with one edit attempt. Compare with Rust and with both baselines' one-shot body edits as controls. Report known-site performance separately. The planned secondary comparison evaluates single-call location and editing against the same workflow in Python and Rust and against GPT++’s separate calls. Replicate all twelve arms on the installed StarCoder2 3B artifact. The selected-site workflow may choose any valid unique expression. Correctness is judged by execution. The copy-based selector can address only one-line expressions with unique text. The experiment measures in-function localization and excludes repository navigation.

The first edit prompt contains target code and public examples. A secondary adaptive result allows a single edit retry only when the first failed public case names a caller. The retry keeps the selected location and receives the previous insertion, public failure and bounded caller excerpts. Failed selections, rejected edits, target mismatches and hidden failures terminate immediately. The primary metric charges every input and output token through the first edit attempt, including failed location calls. Report the adaptive cost separately. No verifier reads the correct replacement to select, repair or score generated text. References and handcrafted fixes calibrate the adapters before inference.

Use the pinned v7 model configurations: greedy seed 42 for location and first edit, seed 43 at temperature 0.25 for a retry, 2,048 context and 240 output tokens per call. Model-side stops include a newline only for the standalone single-line selection, plus the installed transport stops. For combined changes and edits, use the existing per-language FIM boundary stops. Run serially in a fixed shuffled task/arm order for each model. Record prompts, suffixes, settings, every raw response, usage, verdicts and patch hashes for offline replay. One task/model/arm combination is one trial. Estimate uncertainty with the existing 10,000-draw paired task bootstrap. An upper cost ratio at most 0.80 and a lower acceptance difference at least −2 percentage points are the qualification gates. This targeted, small historical sample can guide engineering decisions. Model pretraining exposure and the restricted scalar domains limit generalization.
