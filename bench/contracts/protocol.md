# Finite contracts and checked repair

Freeze the fixtures and candidate expressions before exercising the new verifier or repair tool. The study has three locally authored scalar tasks, ten hand-authored candidate expressions and two sparse input/output examples per task. The candidates include plausible mistakes, a general solution and one deliberately domain-limited solution. Use the original candidate order; the first candidate is the fixed choice for the sparse-example control. All ten hand-authored candidates must pass the supplied examples in each language. Also run the existing public-example search and the new contract-guided search with their default candidate budgets. Each search receives its own documented public input. Do not pass the independent oracle or the extra evaluation inputs to either tool.

| Task | Exact domain and order | Property | Faulty starter's expected first failure |
|---|---|---|---|
| Carry a signed tick | Offset −3 through 4, then carry false/true | Clearing carry preserves the tick; setting it advances by one | (−3, true), second tuple |
| Capacity available | Used 0 through 4, then limit 0 through 4 | Positive unused capacity exactly characterizes availability | (0, 0), first tuple |
| Block number | Offset 0 through 7, then last lane 0 through 3 | The block starts no later than offset, and the subsequent block starts after it | (0, 0), first tuple faults on division by zero |

Enumerate each full Cartesian product in Python independently of GPT++. Compute expected outputs using pair selection, range membership or integer quotient and remainder. Check each original and candidate's per-input results, including faults, by directly executing GPT++, Python and Rust implementations. All values fit signed 64-bit arithmetic. All divisions in the input domains have nonnegative operands; Rust integer division and Python floor division agree there. Python and Rust use translated native expressions, their normal compilers/runtimes and the same finite test inputs. Compare their decisions about exact-domain correctness and their first bad tuple to the GPT++ verifier. This comparison measures semantic parity on this suite. It does not measure developer effort or superiority over existing property-testing tools.

For each hand-authored patch, obtain its actual UTF-8 span from the compiler and run the checked editor. Validate the complete `gpp verify` result against the independent oracle's domain size, first failing arguments or full pass count. Submit the ordered revision-bound candidate list to the contract repair CLI, validate the set of surviving expressions, and check its published fragment against the reported revision. Independently apply each selected search result, then check its behavior on all domain tuples. Archive the source/contract, public cases, candidate lists, verifier/repair results, direct outcomes and source/tool fingerprints. Any discrepancy between implementations fails the study.

Verify the budget boundary on a correct patch for each task with budgets exactly one below and equal to the domain size. The first run must be incomplete, the second must pass after all tuples. Repeat the same insufficient budget through the contract-repair menu and confirm it publishes no claim of verification or fragment. As a separate scope check, run the fixed out-of-domain input list after the candidates and choices are determined. Record those results separately from bounded correctness. The ceiling of 4 in the final carry candidate is deliberate and exposes the scope limit of a passing contract.

No model inference, external services, statistical generalization or timing comparisons are part of this study. Candidate-search results are development observations on a small declared mutation grammar. Each task's examples and extra inputs are fixed in the source fixture file.
