# Paired scalar fragment pilot

Freeze the eight new tasks, independent oracles, compiler, adapters, model settings and prompt templates before collecting the first comparison outcome. Score eight development trials separately using four previously published tasks and the two pilot models. All four conditions use the same task descriptions, public examples and held-out cases.

Each model (DeepSeek Coder 6.7B and Llama 3 8B) gets one initial call and at most one public-feedback repair per condition on each task. The output ceiling is 240 tokens per call, context is 2,048, initial seed is 42 and initial temperature is zero. The earlier full-function protocol retains those settings on repair. All three fragment protocols use seed 43 and temperature 0.25 for the repair after repeated greedy answers in development. The repair includes the failed inputs by name for a public mismatch and a short grammar reminder for recognized GPT++ diagnostics. Use the earlier full-function GPT++ prompt with the updated compiler as a within-task control. In the three fragment conditions, the model continues a prefilled function, supplies either one expression or statements, and receives the current implementation for maintenance. Use the same task-defined edit scope in all three languages. Stop at a closing code fence and retain failures in all denominators. Hidden feedback is available only to the scorer.

Use the recorded model digests, compiler hash, prompts, completions and observed token counts. Compare against both fragment baselines. Python is the preselected primary comparator because it had the highest acceptance in the first pilot. Count every call and compute total input plus output tokens per accepted task. Report host elapsed time separately, including proposal validation. The GPT++ pipeline also validates the bounded edit before execution. The full-function control uses the updated grammar, so its comparison isolates the workflow under that grammar. Cross-study differences also include a workload change.

The development objective is to recover accepted work and reduce token use per accepted task. The design's qualification criteria require the paired acceptance interval's lower endpoint to be at least −2 percentage points and the cost ratio interval's upper endpoint to be at most 0.80. Use a 95% task-cluster percentile bootstrap, keeping the two model results together. A pilot interval estimates sensitivity to these selected task families. Repeated models share task families. Any qualification claim still requires independent, appropriately powered tasks and an explicit cost model.
