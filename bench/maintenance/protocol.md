# Multi-caller maintenance benchmark

Test changes to shared functions used by multiple application callers. Each task has the same old target, caller functions, required behavior, public cases and withheld caller regressions in GPT++, typed Python and Rust. Use scalar reproductions because the current GPT++ compiler supports one scalar module. Record the source and provenance of each change. Provide the file and target name to all arms. This experiment measures authoring a known edit, including obtaining caller context and preserving caller behavior.

## Conditions

Run Qwen2.5-Coder 7B in native fill-in-the-middle mode. Use the same model, one initial call, one optional public-feedback repair and the same input and output budgets in every arm. GPT++, Python and Rust get excerpts selected by the same caller graph traversal, with the same depth and size limits. Give each arm the actual old target, immutable declaration, task and public cases. Only the target expression or body is editable. Use boundary stops for every surface and preserve model defaults. The GPT++ target-only control differs from native GPT++ with caller context solely by removing caller excerpts. A separate exploratory arm uses the bounded Python-syntax input to GPT++ with the same actual GPT++ caller excerpts and current target. Its generated source must pass the GPT++ checker and the same tests.

Use a 2,048-token context and a 240-token completion ceiling. Initial samples use seed 42 and temperature zero. Repairs use seed 43 and temperature 0.25. Repair receives the previous reply and the first public diagnostic or failing call. A public pass ends inference and sends the candidate to withheld evaluation. Stop sequences, requests, output counts, source fingerprints, timings and failed outcomes are recorded. Shuffle the task order and condition order per task with seed 11839. Freeze all task, oracle, runner, selection logic and compiler hashes before the first inference call.

## Acceptance and target

All assigned trials contribute input and output tokens, including failed calls and repairs. An accepted edit passes the checker, public tests and independent withheld tests of the existing target and caller behavior, with bytes outside the target held fixed. Check the reference and old code in every language before running the model. The old code must fail the changed cases and pass the declared preservation cases.

Use typed Python with caller context as the primary comparator, based on its acceptance in the prior benchmark. Also compare with Rust under the equivalent protocol. Report each arm, candidate type, output boundary errors, caller versus direct failing examples, and wall time separately. Report acceptance difference and the ratio of total tokens per accepted edit using 95% task-cluster bootstrap intervals. The acceptance lower bound must be at least −2 percentage points and the cost ratio upper bound at most 0.80 to clear both thresholds. Report the observed distance from 0.80 and the additional acceptance or token reduction implied by the measured budgets. A zero-acceptance arm has undefined cost per success. This eight-task one-model run guides development.
